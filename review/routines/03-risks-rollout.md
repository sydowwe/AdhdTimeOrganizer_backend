## 10. Migration / rollout risks

| Risk | Likelihood | Mitigation | ID |
|---|---|---|---|
| **`CQ-1`'s fix retro-fires months of resets on every account.** Every user has a Monthly (30d, anchor 1) and a Yearly (365d, anchor 1) period whose `LastResetAt` is still `null`, so `ComputeNextReset` falls back to `CreatedTimestamp` (`RoutineResetService.cs:14`). The first sweep after the fix finds them due, and — because of `CQ-8` — advances one cycle per run while emitting one `RoutinePeriodEnded` notification each. A one-year-old account gets twelve "you missed a month" notifications over twelve nights, each with a real streak evaluation against items that were never in a valid cycle. | **High** — certain, not speculative | Ship `CQ-8`'s bounded catch-up loop **in the same release**, and suppress the summary notification for cycles collapsed by catch-up. Consider a one-off data migration that stamps `LastResetAt = <now, snapped back to the anchor>` on every period with `LengthInDays IN (30, 365) AND reset_anchor_day <> 0 AND last_reset_at IS NULL`, so the fix starts from "current" rather than from account creation. | `MIG-1` |
| **`SEC-1`'s fix does not clean up rows already written.** Adding the ownership check stops new cross-tenant writes; any `routine_todo_list` row whose `user_id` differs from its period's `user_id` stays, and keeps corrupting the victim's counts on every sweep. | Low that it has been exploited; certain that nothing detects it | Ship a detection query with the fix — `SELECT r.id FROM routines.routine_todo_list r JOIN routines.routine_time_period p ON p.id = r.time_period_id WHERE r.user_id <> p.user_id` (schema-qualified: hand-written SQL is not qualified for you here) — and decide delete-vs-reassign before the release, not after. Add it as a permanent integrity assertion, since neither the FK nor the query filter enforces it. | `MIG-2` |
| **`CQ-9`'s fix is a table rename on live data, not a no-op.** Promoting `RoutinePeriodCompletion` to `BaseTableEntity` renames `routine_period_completions` → `routine_period_completion`, adds `row_version`, and replaces `created_at` with the base's `created_timestamp`/`modified_timestamp` pair. It also breaks `ModuleSchemaTests.cs:61`, which pins the plural name. | Medium if attempted casually | **Recommend declining.** The current shape is ugly but stable and pinned; the cost is a rename migration plus a test edit for no behavioural gain. If taken anyway, do it alone, in its own release, and check the generated migration by hand before applying — `summary.md`'s "class names are table names" gotcha means a rename here *is* a migration even though nothing about the type moved. | `MIG-3` |
| **`CQ-3`'s new validator rules reject values already in the database.** `LengthInDays > 365` and `HistoryDepth` outside `1..100` are already impossible — both DB checks predate this — so the rules are additive with no data risk. | None | Ship freely. The only visible change is that the 400 gains a field key, which the SPA's form binding will start attaching to an input. Worth a note to whoever owns the frontend. | `MIG-4` |
| **`SEC-2`'s fix is a breaking API change if any client sends `IsDone` on `PUT`.** Dropping the three fields from `UpdateRoutineTodoListRequest` means a client relying on the `PUT` to complete a routine silently stops completing it. | Low — the SPA uses the toggle endpoint | Grep the frontend for `IsDone` in the routine update payload before dropping the field. If a caller exists, route it through the toggle logic instead of removing the field, and land the removal in a later release. | `MIG-5` |
| **Drift risk — none found.** There is no sandbox or duplicate copy of this module. `AdhdTimeOrganizer/reference/mojaCore/` is foreign reference code that does not contain a routines equivalent, and the csproj forbids a host reference structurally. The one outbound edge (`Routines → TodoLists`) is verified one-way by inspection and by `SeamWiringTests`. | — | Nothing to do. Recorded so the question is not re-opened. | `MIG-6` |
| **Five silent registration points remain, and only three are guarded.** `summary.md` lists FastEndpoints `o.Assemblies`, `ModuleServiceExtensions.ModuleAssemblies`, `AppDbContext.ApplyHostConfigurations`, the solution file, and `AddHostedService<RoutinesScheduledJobsRegistrar>()`. `ModuleWiringTests` covers routing (`ModuleEndpoints_AreRouted`), single registration (`ModuleServices_AreRegisteredExactlyOnce`), model mapping (`ModuleEntities_AreMappedAndQueryable`) and the registrar (`BootRegistrars_…`). | Low, but every failure mode is silent | No action needed today — this is better guarded than the first pass credited. Keep it that way: any new routines endpoint added while `ModuleEndpoints_AreRouted`'s route list is not updated is invisible. | `MIG-7` |

## Audit-log gaps

| Gap | Detail | ID |
|---|---|---|
| **Nothing in this module is audited, including the two things a user would dispute.** CLAUDE.md states auditing exists in Framework but is not wired up here, so this is a solution-wide gap rather than a Routines defect — but Routines is where it bites hardest. `Streak` / `BestStreak` / `FreezesRemaining` are mutated by three request paths and two unauthenticated sweeps, and a user who loses a streak (via `CQ-1`, `CQ-6`, `CQ-7`, `CQ-13`, or an ordinary lapsed grace window) has no record of what happened or which path did it. The `RoutinePeriodCompletion` ledger is the closest thing to a trail and it only records counts, not streak transitions. | Not fixable inside this module. When auditing is wired up, `RoutineTimePeriod` should be among the first entities enrolled, and `StreakOutcome` should be part of the captured payload — it is already computed and returned by `TryReset` (`RoutineResetService.cs:242-252`) precisely because "only this method sees the streak on both sides of the evaluation". | `AUDIT-1` |
| **No `ExecuteUpdateAsync` / `ExecuteDeleteAsync` anywhere in the module.** Every mutation goes through tracked entities and `SaveChangesAsync`, so nothing here would bypass the interceptor once one exists. Verified by search across `application/`, `domain/` and `infrastructure/`. | No action. Recorded so it is not re-derived — and as a constraint worth preserving: the obvious "performance fix" for `PERF-3` (bulk-update the swept periods) would break this and should be rejected on those grounds as well as the correctness ones. | `AUDIT-2` |
| **The dev seeder truncates outside the change tracker.** `RoutineTodoListSeeder.TruncateTable` issues `TRUNCATE … RESTART IDENTITY CASCADE` via `TruncateTableCascadeAsync<RoutineTodoList>()`. That is by design for a dev fixture, and the framework helper schema-qualifies the table name from the EF model (`SeederExtensions.cs:79-96`), so it does not fall foul of CLAUDE.md's unqualified-SQL trap. It is dev-only and gated behind `IPerUserDevSeeder`. | No action. Listed because a bulk-op scan will flag it and it should be dismissed on sight, not re-investigated. | `AUDIT-3` |
| **No `[AuditIgnore]` / `[NoAudit]` attributes are needed here.** Nothing in the four entities is a secret, a token or special-category personal data: text, colour, integers, dates and two idempotency marks. The only PII-adjacent field is `RoutineTimePeriod.Text` (user-authored), which `RoutinePeriodNotificationService` already keeps out of logs deliberately (`:64-67`, `:82`) — a good precedent to copy if audit payloads ever carry it. | No action. | `AUDIT-4` |
